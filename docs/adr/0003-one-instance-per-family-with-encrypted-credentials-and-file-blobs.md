# One Instance serves one Family; credentials are encrypted at rest and blobs live in files

Every Instance has its own database and serves exactly one Family, so the Family is implied by the database: there is no `families` table, no other table carries a `family_id` column, and no query filters by Family. A provider hosting Family Agenda as a service runs one Instance per Family, which keeps tenants isolated without row-level security. Stateless plugins can still be shared between Instances, because they hold nothing (ADR-0001).

Postgres dumps get copied, attached to bug reports and uploaded as backups, so Source credentials never appear in them in clear text. A `SecretStore` port encrypts each credential with the master key, which is never in Postgres. Raw attachments such as PDFs and images live behind a `BlobStore` port, by default the filesystem; Postgres holds only their metadata. Files and secrets that nothing refers to any more are swept (ADR-0005).

## Consequences

- A backup is a Postgres dump plus the blob volume, without the master key. The Admin keeps a Recovery Kit; without it a restored backup cannot open Source credentials.
- Secrets leave the core only decrypted inside a call to the plugin of their own Source Type (ADR-0001).
- Several Families on one Instance, or a shared multi-tenant database, would need every table and query touched.

## Amendment: the Family id (plugin contract 3.0)

A Family is named by one identifier, its Family id: a random UUID made with the `family` row and kept in its `family_id` column. It names the Family only outside its database: the ticket of a plugin call carries it (ADR-0001); since the Egress Proxy decides from the ticket alone, nothing checks it there yet. Inside the database nothing changes: there is still no `families` table, no other table carries a `family_id` column, and no query filters by Family. Today an Instance answers only for its own Family id; when one Instance serves several Families, each in its own database, the same id is how a request from a shared stateless plugin's Egress Proxy says which database to ask.

## Amendment: the Family id is chosen or drawn once

The Family id is drawn at random when a Family is first prepared, unless the operator gives one before it exists (`FAMILY_ID`, or the body of the Triggered operation `prepare-family`). It is written in the same transaction as the migrations that create the `family` row, so a failed start leaves no random id behind. Once a database holds an id, it never changes: Preparing the Family with a different one is refused before anything changes. Preparing works on the Family's database, not on a booted Family, so that an Instance of several Families can prepare an empty database for a new one.

## Amendment: a folder per Family in the blob volume

The file-based BlobStore keeps a Family's blobs at `<blob directory>/<family id>/<blob reference>`, in a folder readable by its owner only, so that several Families can share one blob volume without seeing each other's files. A blob is written once under its final name: its reference is random and handed out only after the write, so nothing reads it half-written. Preparing the Family moves the blobs of the earlier layout, files named by a blob reference in the top level of the volume, into the Family's folder; running it again finishes an interrupted move.

## Amendment: one core may serve several Families, given a Context per request

A core runs in one of two modes, chosen explicitly by `CONTEXT_MODE`. In **fixed** mode, the default, nothing changes: the environment names the one Family, its database, master key file and blob directory. In **supplied** mode the core has none of these: every request carries the Context of the Family it is for, and the core opens the database the Context names, uses its family key in place of the master key for the Family's Source credentials, and keeps the Family's blobs in its folder of the blob location the Context names. Each Family still has a database of its own, so everything above holds per Family: no table carries a Family column and no query filters by Family. Any core can then serve any Family, and one core several. The Family's time zone, its public address (its path prefix included) and its Identity Provider (ADR-0007) come with its Context too; in fixed mode they keep coming from the environment.

- **Sealed by a trusted caller.** A Context is the JSON `{ familyId, databaseUrl, familyKey, blobDirectory, timeZone, publicUrl, identityProvider?, expiresAt }`, encrypted with AES-256-GCM under a key derived by HKDF-SHA-256 from `CONTEXT_KEY`, which only the core and the trusted caller in front of it (a gateway) hold, and written `v1.<iv>.<ciphertext>.<tag>` in base64url. The authentication tag makes it tamper-proof and the encryption keeps the family key and the database password out of every header log in between; a fresh random IV each time means no two sealings look alike. `family-agenda seal-context` seals one from standard input. The caller seals Contexts that expire within minutes; the core refuses an expired one, after 30 seconds of skew for clocks that differ, and one that expires more than a day ahead, the longest `seal-context` seals too.
- **How it reaches the core.** In the request header `X-Family-Context`, and nowhere else: not in the query, a cookie or a form. The core removes the header before the Family's pages see the request and never answers with it.
- **Never on a port published to browsers.** A core in supplied mode opens no listener on `PORT`, the pages port a compose file publishes. It listens only on the caller port, `CALLER_PORT`, which it requires and which must differ from `PORT`; no compose file publishes it. It offers no Triggered operations yet. The deployment assumption is that the caller port is reachable from the trusted caller only, on a network of their own: browsers reach the caller, which authenticates them, decides their Family, seals its Context and forwards the request. A browser never holds the Context key, and the caller never hands it a Context. A fixed-mode core reads no Context at all, whatever its requests carry.
- **Refusal.** A request without a Context, or with one that does not open (another key, altered, expired, not a Context), gets `401` and opens nothing. A Context whose Family id differs from the one its database holds gets `403`, as Preparing the Family refuses a different id. Opening a Family writes nothing: it reads the stored Family id and the migrations applied, and a database that holds no Family, or whose schema is not this version's, gets `409` `family-not-prepared` and is left as it is. Preparing a supplied Family, including the move of blobs of the earlier layout, is a Triggered operation of its own (#381), never part of opening one, so a shared blob directory is never touched on opening. A database that cannot be reached gets `503`. A Context that opens but carries settings the core does not take, such as an unknown time zone or incomplete Identity Provider settings, gets `400` naming what is wrong, as the environment variables are named in fixed mode; it is sealed with the Context key, so only the trusted caller learns why, and never a value. Only the health check answers without a Context; it names no Family. A refusal is logged without the Context, the family key or the database URL, only the Family id and the kind of error.
- **Held in memory only, briefly.** What a core derives from a Context, the database connections and the wired Family, is kept in memory, keyed by a hash of the Family id, database, family key and blob location, so that a resealed Context of the same Family reuses it, and closed once no request has used it for five minutes. The connection pool closes its own idle connections after ten seconds. No Context, family key or database password is written to disk.
- **No fallback.** In supplied mode a request without a valid Context is refused; the core never falls back to a fixed Family, and it refuses to start with `DATABASE_URL`, `FAMILY_ID`, `MASTER_KEY_FILE` or `BLOB_DIRECTORY` set. With `CONTEXT_KEY` set it refuses to start in fixed mode, and in supplied mode it refuses to start without one; the worker and the command-line Admin commands run in fixed mode only.
- **The Family's own settings.** `timeZone` is required, an IANA name such as `Europe/Berlin`. `publicUrl` is required, an http or https address: the caller removes the path prefix from a request and states it here, and the core emits every link, redirect, cookie path, web manifest, Agenda feed address and the single sign-on redirect URI below it. `identityProvider`, `{ issuerUrl, clientId, clientSecret, requiredGroup? }`, is optional: without it the Family is not offered single sign-on. None of them falls back to the environment: a core in supplied mode refuses to start with `PUBLIC_URL` or an `OIDC_*` variable set. An opened Family is kept per Family and per these settings, so two Contexts of one Family with different settings never share a wired Family.

The consequence above, that several Families on one Instance would need every table touched, no longer stands for Families each in a database of their own; it still stands for a shared database.
