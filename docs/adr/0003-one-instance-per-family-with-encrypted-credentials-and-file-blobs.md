# One Instance serves one Family; credentials are encrypted at rest and blobs live in files

Every Instance has its own database and serves exactly one Family, so the Family is implied by the database: there is no `families` table, no other table carries a `family_id` column, and no query filters by Family. A provider hosting Family Agenda as a service runs one Instance per Family, which keeps tenants isolated without row-level security. Stateless plugins can still be shared between Instances, because they hold nothing (ADR-0001).

Postgres dumps get copied, attached to bug reports and uploaded as backups, so Source credentials never appear in them in clear text. A `SecretStore` port encrypts each credential with the master key, which is never in Postgres. Raw attachments such as PDFs and images live behind a `BlobStore` port, by default the filesystem; Postgres holds only their metadata. Files and secrets that nothing refers to any more are swept (ADR-0005).

## Consequences

- A backup is a Postgres dump plus the blob volume, without the master key. The Admin keeps a Recovery Kit; without it a restored backup cannot open Source credentials.
- Secrets leave the core only decrypted inside a call to the plugin of their own Source Type (ADR-0001).
- Several Families on one Instance, or a shared multi-tenant database, would need every table and query touched.

## Amendment: the Family id (plugin contract 3.0)

A Family is named by one identifier, its Family id: a random UUID made with the `family` row and kept in its `family_id` column. It names the Family only outside its database: the ticket of a plugin call carries it (ADR-0001); since the Egress Proxy decides from the ticket alone, nothing checks it there yet. Inside the database nothing changes: there is still no `families` table, no other table carries a `family_id` column, and no query filters by Family. Today an Instance answers only for its own Family id; when one Instance serves several Families, each in its own database, the same id is how a request from a shared stateless plugin's Egress Proxy says which database to ask.

## Amendment: the Family id is chosen or drawn once

The Family id is drawn at random when a Family is first prepared, unless the operator gives one before it exists (`FAMILY_ID`, or in supplied mode the Context of the Family). It is written in the same transaction as the migrations that create the `family` row, so a failed start leaves no random id behind. Once a database holds an id, it never changes: Preparing the Family with a different one is refused before anything changes. The model of preparing ([`specs/registration`](../../specs/registration), ADR-0012) checks this: two cores preparing at once, or one dying midway, keep one Family id, and a failed start leaves no random id behind; writing the id after the migrations commit would. Preparing works on the Family's database, not on a booted Family, so that an Instance of several Families can prepare an empty database for a new one.

## Amendment: a folder per Family in the blob volume

The file-based BlobStore keeps a Family's blobs at `<blob directory>/<family id>/<blob reference>`, in a folder readable by its owner only, so that several Families can share one blob volume without seeing each other's files. A blob is written once under its final name: its reference is random and handed out only after the write, so nothing reads it half-written. Preparing the Family moves the blobs of the earlier layout, files named by a blob reference in the top level of the volume, into the Family's folder; running it again finishes an interrupted move.

## Amendment: one core may serve several Families, given a Context per request

A core runs in one of two modes, chosen explicitly by `CONTEXT_MODE`. In **fixed** mode, the default, nothing changes: the environment names the one Family, its database, master key file and blob directory. In **supplied** mode the core has none of these: every request carries the Context of the Family it is for, and the core opens the database the Context names, uses its family key in place of the master key for the Family's Source credentials, and keeps the Family's blobs in its folder of the blob location the Context names. Each Family still has a database of its own, so everything above holds per Family: no table carries a Family column and no query filters by Family. Any core can then serve any Family, and one core several. The Family's time zone, its public address (its path prefix included) come with its Context too; the one Identity Provider of the deployment comes from the environment (ADR-0009); in fixed mode they keep coming from the environment.

- **Sealed by a trusted caller.** A Context is the JSON `{ familyId, databaseUrl, familyKey, blobDirectory, timeZone, publicUrl, sections?, expiresAt }`, encrypted with AES-256-GCM under a key derived by HKDF-SHA-256 from `CONTEXT_KEY`, which only the core and the trusted caller in front of it (a gateway) hold, and written `v1.<iv>.<ciphertext>.<tag>` in base64url. The authentication tag makes it tamper-proof and the encryption keeps the family key and the database password out of every header log in between; a fresh random IV each time means no two sealings look alike. `family-agenda seal-context` seals one from standard input. The caller seals Contexts that expire within minutes; the core refuses an expired one, after 30 seconds of skew for clocks that differ, and one that expires more than a day ahead, the longest `seal-context` seals too.
- **How it reaches the core.** In the request header `X-Family-Context`, and nowhere else: not in the query, a cookie or a form. The core removes the header before the Family's pages see the request and never answers with it.
- **Never on a port published to browsers.** A core in supplied mode opens no listener on `PORT`, the pages port a compose file publishes. It listens only on the caller port, `CALLER_PORT`, which it requires and which must differ from `PORT`; no compose file publishes it. It offers no Triggered operations yet (see the amendment below). The deployment assumption is that the caller port is reachable from the trusted caller only, on a network of their own: browsers reach the caller, which authenticates them, decides their Family, seals its Context and forwards the request. A browser never holds the Context key, and the caller never hands it a Context. A fixed-mode core reads no Context at all, whatever its requests carry.
- **Refusal.** A request without a Context, or with one that does not open (another key, altered, expired, not a Context), gets `401` and opens nothing. A Context whose Family id differs from the one its database holds gets `403`, as Preparing the Family refuses a different id. Opening a Family that this release has not prepared prepares it first, and a shared blob directory is never touched on opening (see the amendment "Preparing on opening", which replaces a `409` `family-not-prepared` here and the Triggered operation that prepared a Family). A database that cannot be reached gets `503`. A Context that opens but carries settings the core does not take, such as an unknown time zone or an `identityProvider` (ADR-0009), gets `400` naming what is wrong, as the environment variables are named in fixed mode; it is sealed with the Context key, so only the trusted caller learns why, and never a value. Only the health check answers without a Context; it names no Family. A refusal is logged without the Context, the family key or the database URL, only the Family id and the kind of error.
- **Held in memory only, briefly.** What a core derives from a Context, the database connections and the wired Family, is kept in memory, keyed by a hash of the Family id, database, family key, blob location, time zone and public address, so that a resealed Context of the same Family reuses it, and closed once no request has used it for five minutes. The connection pool closes its own idle connections after ten seconds. No Context, family key or database password is written to disk.
- **No fallback.** In supplied mode a request without a valid Context is refused; the core never falls back to a fixed Family, and it refuses to start with `DATABASE_URL`, `FAMILY_ID`, `MASTER_KEY_FILE` or `BLOB_DIRECTORY` set. With `CONTEXT_KEY` set it refuses to start in fixed mode, and in supplied mode it refuses to start without one; the worker and the command-line Admin commands run in fixed mode only.
- **The Family's own settings.** `timeZone` is required, an IANA name such as `Europe/Berlin`. `publicUrl` is required, an http or https address: the caller removes the path prefix from a request and states it here, and the core emits every link, redirect, cookie path, web manifest, Agenda feed address and the single sign-on redirect URI below it. Neither falls back to the environment: a core in supplied mode refuses to start with `PUBLIC_URL` set. The Identity Provider is no setting of a Family's: a Context carrying `identityProvider` is refused (ADR-0009). An opened Family is kept per Family and per these settings, so two Contexts of one Family with different settings never share a wired Family.
- **Sections of the platform.** `sections` is optional: entries the platform in front adds to the Admin area, each a label, the address the browser loads its content from as an HTML fragment, and optionally the one Admin it is for. The core knows nothing of what they hold, such as a contract with the operator, and stores nothing: each request shows those of its own Context, so they are no setting an opened Family is kept by. An address must be of the origin of `publicUrl`, as the fragment lands in the Admin page, trusted like the Context and asked for with the browser's cookies. What a fragment may rely on: [docs/configuration.md](../configuration.md#sections-in-the-admin-area).

The consequence above, that several Families on one Instance would need every table touched, no longer stands for Families each in a database of their own; it still stands for a shared database.

## Amendment: Triggered operations in supplied mode

A core in supplied mode does no work for a Family of its own: it runs no schedule and prepares no Family when it starts, and the `worker` refuses supplied mode. Background work and preparing are Triggered operations a caller runs per Family (#381). Preparing is no longer one of them: the amendment "Preparing on opening" below replaces what this one says about it, `409` `family-not-prepared` included.

- **Token and Context.** With a trigger token, the core serves the Triggered operations on their own unpublished port, as a fixed core does. Every trigger carries both: the token guards the port, checked first; the Context, sealed as for a page request, picks the Family. One without a valid Context is refused and opens nothing.
- **Read-only, except preparing.** Due work, the purge, the secret sweep, entering an Admin and resetting a password open the Family as a page request does, sharing its opened Family, and get the same refusals: `403` for a Context whose Family id differs from the one its database holds, `409` `family-not-prepared` for a database not prepared by this release, `503` for one that cannot be reached. Due work's plugin calls are ticketed for the Context's Family id, and a trigger during a run of the same database waits for that run.
- **Preparing the Family** is the one operation that migrates and writes a Family id, always the Context's: an empty database becomes usable with the id the caller chose. A database holding another id is refused with `409` `family-id-differs`, as in fixed mode, where it is a conflict with the stored state; opening answers `403` because there the Context is not allowed to that database. A database migrated by a newer release (`migrated-by-newer-release`) or holding the old data model (`old-data-model`) is refused with `409`, one that cannot be reached with `503`; each changes nothing. It moves no blobs: the blob location is shared, and blobs of the earlier layout belong to the upgrade of a fixed Instance.
- **Per Family, in turn.** Prepares of one database take turns; those of other databases run meanwhile. While one runs, requests and triggers for that database wait, and what was opened on the schema before is dropped before anyone reuses it, so nothing runs on a schema half migrated by this core.

## Amendment: Preparing on opening

Preparing a supplied Family as a Triggered operation of its own, before a core may open it, asked a caller for two calls to reach one core, and to keep track of which release prepared which Family. Instead, opening a Family prepares it, and the Triggered operation `prepare-family` is gone, in both modes: a fixed core prepares its Family when it starts, as before, and a core in supplied mode when it opens one (#405). This replaces "Read-only, except preparing", "Preparing the Family" and "Per Family, in turn" above.

- **Prepared on first opening.** The first request or trigger whose Context names a database this release has not prepared, an empty one or one an older release prepared, prepares it with the Context's Family id, and is then served as usual. Opening checks first, without writing: a database a newer release migrated is refused with `409` `migrated-by-newer-release`, one of the old data model with `409` `old-data-model`, one that holds another Family id with `403` `family-id-differs`. During a rolling update, an older core so refuses a database a newer one migrated, and the caller tries another core; older cores are replaced soon after. Preparing moves no blobs: the blob location is shared, and blobs of the earlier layout belong to the upgrade of a fixed Instance.
- **Once, however many open it.** Requests opening a database while it is prepared wait for that one prepare; across cores, the migration lock in Postgres serialises them, and preparing again changes nothing. A request waits up to 20 seconds; after that it is answered `503` `migrating`, the preparing goes on, and a retry is served once it is done.
- **Checked again while open.** A core keeps an opened Family for minutes, so a request that reuses it checks its schema again, at most every 5 seconds, sharing the check with the requests meanwhile. A core that finds a newer release migrated it drops the opened Family, closing it once its requests are done, and answers `409` `migrated-by-newer-release`, as on first opening. A schema check per request was weighed and left out: the throttled one costs one small query every few seconds per opened Family, and a shared advisory lock per request against the migrator's exclusive one would cost a round trip on every request, queue requests behind a waiting migration, and protect nothing once it has committed (docs/research/locking-a-database-during-migrations.md).
- **The migration never waits long for a table.** Each migration statement waits at most 5 seconds for a lock, such as a table a long transaction of another core holds (`lock_timeout`); a migration that times out has changed nothing, its one transaction rolled back, and is tried again, three times in all. A migration waiting for a table makes every request queued behind it on that table wait too, so it gives up rather than stall the Family. The database itself is not shut against other cores: no reviewed migration tool does so, and it would need privileges a core has no need for.
- <a id="expand-contract"></a>**Migrations expand, then contract.** During a rolling update, cores of the release before and of the new one serve one Family side by side, the older ones until the check above makes them refuse it. So a migration only adds what the code of the release before still runs on: new tables, new columns that are nullable or have a default, new indexes. What it drops or renames, a column, a table, a constraint the old code relies on, goes in a migration of a later release than the one whose code stopped using it; a rename is an addition, a copy and, a release later, the drop. A data change keeps the old code's reads and writes valid. Earlier migrations such as `0004_identity_provider_from_environment` and `0009_family_id` predate this rule and would now each be two. The rule is model-checked in `specs/rolling-update` (ADR-0012): no core reads or writes a column that is gone, none reads a value another release's write did not reach, and the update can always finish. A rename of a column the old code writes takes four releases after the old one: add and copy, writing both; copy again and read the new one; stop writing the old one; drop it.
- **Source Types.** Opening a database already prepared by this release migrates nothing and writes no Family id; it records the Source Types and catalogue entries seen for the first time, as a fixed core does when it starts, so a newly installed plugin reaches every Family without a step of the caller's.
