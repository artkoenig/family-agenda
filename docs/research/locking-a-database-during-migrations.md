# Locking a database during schema migrations

Question (issue #405): how do applications with several instances (rolling deploys) keep a Postgres database safe during schema migrations? Is it normal to lock the whole database against the other app instances while a migration runs? Which mechanisms does Postgres have for that, and what do they guarantee? And should a core lock a Family's database against the other cores while it migrates it?

Research date: 2026-11-16. Note: every host could be fetched. PostgreSQL claims come from the current manual, the PostgreSQL wiki and the lock manager's README in the PostgreSQL source. Tool claims were read from each tool's GitHub source or official docs. For drizzle-orm, the source is the version this repo installs (0.45.4, in `node_modules`) and `main` on GitHub, which have the same `migrate`. Items marked *unverified* need checking before anyone relies on them.

## Short answer

- **Locking the whole database against the other app instances is not common practice.** None of the tools reviewed here (drizzle, Flyway, Liquibase, Rails, Django, Prisma, golang-migrate, Sqitch, pgroll, Reshape) does it or offers it. The common practice has two parts. First, **only one migrator runs at a time**, enforced with an advisory lock or a lock table. Second, **migrations are written to be backwards compatible ("expand/contract")**, so that old and new app versions can use the same database during a rolling deploy. Short `lock_timeout`s keep the DDL itself from stalling traffic. The alternative is a maintenance window (stop every old instance, migrate, start the new ones). That is the only arrangement in which "nobody else touches the database" holds.
- **Postgres has the building blocks but no "migration mode".** Advisory locks (cooperative only), the table locks DDL takes automatically, transactional DDL, `lock_timeout`, and connection-level controls (`ALLOW_CONNECTIONS`, `CONNECTION LIMIT`, `REVOKE CONNECT`, `pg_terminate_backend`). The connection-level controls need owner or superuser rights and act only on *new* connections, unless sessions are also terminated.

## Findings

### 1. Advisory locks: what they are and what they guarantee

- Advisory locks have "application-defined meanings". The system "does not enforce their use — it is up to the application to use them correctly" ([PG docs, 13.3.5 Advisory Locks](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS)). **They are cooperative only.** A session that never asks for the lock is not held back by it, and no table is protected by one.
- **Session vs. transaction level.** A session-level lock "is held until explicitly released or the session ends" and does not honour transaction semantics: it survives a rollback. A transaction-level lock is released automatically at the end of the transaction and has no explicit unlock. Session- and transaction-level requests for the same key block each other ([PG docs, 13.3.5](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS)). Session-level locks stack: a key locked three times needs three unlocks. `pg_advisory_unlock_all()` is "implicitly invoked at session end, even if the client disconnects ungracefully" ([PG docs, 9.28.10 Advisory Lock Functions](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)). So a crashed migrator cannot leave a stale lock behind, unlike a lock row in a table.
- **Shared vs. exclusive.** `pg_advisory_lock` takes an exclusive session-level lock and `pg_advisory_lock_shared` a shared one, both "waiting if necessary". "A shared lock does not conflict with other shared locks on the same resource, only with exclusive locks." Each has an `_xact_` variant (transaction level) and a `pg_try_` variant that returns `false` instead of waiting ([PG docs, 9.28.10](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)).
- **Scope.** "Advisory locks are local to each database" ([PG docs, pg_locks](https://www.postgresql.org/docs/current/view-pg-locks.html)). The same key in two databases on one server names two independent locks.
- **Queueing.** Advisory locks live in the same lock manager as table locks ([PG docs, 13.3.5](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS)). That manager grants conflicting requests "in order of arrival": a waiter is woken only if its request does not conflict with "the requests of prior un-wakable waiters" ([PostgreSQL source, `src/backend/storage/lmgr/README`](https://github.com/postgres/postgres/blob/master/src/backend/storage/lmgr/README)). So a waiting exclusive request holds back later shared requests, and the exclusive waiter is not starved.
- **Connection poolers.** A session-level lock needs a stable session. Rails tells PgBouncer users to turn advisory locks off ([Rails guides, Configuring a PostgreSQL Database](https://guides.rubyonrails.org/configuring.html#configuring-a-postgresql-database)). Prisma's docs say session state, advisory locks included, "is lost after each transaction boundary" behind PgBouncer in transaction mode ([Prisma docs, llms-full.txt, connection pooling](https://www.prisma.io/docs/llms-full.txt)).
- Whether `lock_timeout` also cuts short a `pg_advisory_lock` wait is *unverified*. Its documentation names "a table, index, row, or other database object" ([PG docs, lock_timeout](https://www.postgresql.org/docs/current/runtime-config-client.html#GUC-LOCK-TIMEOUT)). Advisory locks are not named there.

### 2. The locks DDL takes by itself, transactional DDL, and the lock queue

- Most commands take table locks automatically. ACCESS EXCLUSIVE "conflicts with locks of all modes" and "guarantees that the holder is the only transaction accessing the table in any way". It is also the only mode that blocks a plain `SELECT`. A transaction waiting for a lock waits "indefinitely" unless a deadlock is detected ([PG docs, 13.3.1 Table-Level Locks](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-TABLES)).
- `ALTER TABLE`: "An ACCESS EXCLUSIVE lock is acquired unless explicitly noted". Exceptions include `ADD FOREIGN KEY` (SHARE ROW EXCLUSIVE), `VALIDATE CONSTRAINT` and `SET STATISTICS` (SHARE UPDATE EXCLUSIVE). `ADD CONSTRAINT ... NOT VALID` followed by `VALIDATE CONSTRAINT` avoids locking out updates during the scan ([PG docs, ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)). `CREATE INDEX CONCURRENTLY` avoids blocking writes but "cannot" run in a transaction block ([PG docs, CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html)).
- **Transactional DDL.** Postgres can roll back DDL: "You can't recover from an add/drop on a database or tablespace, but all other catalog operations are reversible" ([PostgreSQL wiki, Transactional DDL](https://wiki.postgresql.org/wiki/Transactional_DDL_in_PostgreSQL:_A_Competitive_Analysis)). A migration in one transaction therefore commits all or nothing. Other sessions see the old schema or the new one, never a half-applied one. The locks it takes are held until commit, so in-flight work on the touched tables is already excluded while it runs.
- **The lock-queue problem.** Requests are granted in arrival order (section 1). An `ALTER TABLE` waiting for ACCESS EXCLUSIVE behind one long-running transaction therefore blocks every later query on that table, plain reads included, until it gets the lock and commits ([lmgr README](https://github.com/postgres/postgres/blob/master/src/backend/storage/lmgr/README); [PG docs, 13.3.1](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-TABLES)). A short DDL statement can so take an application down.
- **The remedy is `lock_timeout`.** It aborts "any statement that waits longer than the specified amount of time while attempting to acquire a lock", applied "separately to each lock acquisition attempt". The default is 0 (off). `statement_timeout` bounds total statement time. The docs advise against setting either in `postgresql.conf`, because they would affect all sessions ([PG docs, Client Connection Defaults](https://www.postgresql.org/docs/current/runtime-config-client.html#GUC-LOCK-TIMEOUT)). `SET LOCAL` limits a setting to the current transaction ([PG docs, SET](https://www.postgresql.org/docs/current/sql-set.html)). strong_migrations calls a short lock timeout for migrations "extremely important ... if a migration can't acquire a lock in a timely manner, other statements won't be stuck behind it". It suggests 10 s, a long statement timeout, and optional retries of the whole migration when the timeout hits inside the DDL transaction ([strong_migrations README](https://github.com/ankane/strong_migrations/blob/master/README.md#migration-timeouts)).

### 3. Blocking connections at database level

| Mechanism | Effect | Who may do it | Existing sessions |
|---|---|---|---|
| `ALTER DATABASE d ALLOW_CONNECTIONS false` | "no one can connect to this database" ([ALTER DATABASE](https://www.postgresql.org/docs/current/sql-alterdatabase.html)); the flag exists to protect `template0` ([pg_database](https://www.postgresql.org/docs/current/catalog-pg-database.html)) | database owner or superuser ([ALTER DATABASE](https://www.postgresql.org/docs/current/sql-alterdatabase.html)) | not terminated: the docs speak only of connecting (*unverified* in the docs' own words). The migrator's own *new* connections are refused too, superuser or not (*unverified*) |
| `ALTER DATABASE d CONNECTION LIMIT n` | caps concurrent connections; "only enforced approximately" and "not enforced against superusers or background worker processes" ([CREATE DATABASE, Notes](https://www.postgresql.org/docs/current/sql-createdatabase.html)) | owner or superuser | not terminated (*unverified* in the docs' own words) |
| `REVOKE CONNECT ON DATABASE d FROM PUBLIC` (and from the app role) | CONNECT "is checked at connection startup". PUBLIC has CONNECT on databases by default. The owner always keeps all privileges ([PG docs, 5.8 Privileges](https://www.postgresql.org/docs/current/ddl-priv.html)) | owner (or a role with grant option) | unaffected, since the check happens only at startup |
| `pg_terminate_backend(pid, timeout)` | sends SIGTERM and ends the session; with a timeout it waits for the process to end ([PG docs, 9.28.2 Server Signaling](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-SIGNAL)) | a member of the target's role, or a role with `pg_signal_backend`; only superusers may end superuser backends (same source) | the only one of the four that ends them; their open transactions roll back |

A real stop-the-world from inside Postgres therefore takes two steps: block new connections (one of the first three), then terminate the existing ones. That needs owner rights or `pg_signal_backend`. It kills in-flight requests, and it shuts out every other instance, including ones that would only have read. No tool reviewed here does this as part of migrating.

### 4. What migration tools actually do

| Tool | One migrator at a time | Transactions |
|---|---|---|
| **drizzle-orm** (pg migrator) | **No lock of its own.** `PgDialect.migrate` creates the `drizzle` schema and `__drizzle_migrations` table, reads the last applied row *outside* any transaction, then runs every pending migration in **one** `session.transaction(...)`, inserting a row per migration ([drizzle-orm `pg-core/dialect.ts`](https://github.com/drizzle-team/drizzle-orm/blob/main/drizzle-orm/src/pg-core/dialect.ts)). Two concurrent migrators would both see the same "last" row. Serialising them is left to the caller | all pending migrations in one transaction |
| **Flyway** | `pg_try_advisory_xact_lock` by default, or `pg_try_advisory_lock` when `postgresql.transactional.lock=false`, retried until it gets the lock ([Flyway `PostgreSQLAdvisoryLockTemplate.java`](https://github.com/flyway/flyway/blob/main/flyway-database/flyway-database-postgresql/src/main/java/org/flywaydb/database/postgresql/PostgreSQLAdvisoryLockTemplate.java)). The docs say to use session locks for statements such as `CREATE INDEX CONCURRENTLY` ([Flyway docs](https://documentation.red-gate.com/fd/flyway-postgresql-transactional-lock-setting-277579114.html)) | per migration |
| **Liquibase** | a lock *row* in `DATABASECHANGELOGLOCK`, made for "multiple servers in a cluster auto-run[ning] Liquibase on startup". It "may be left as locked" after an unclean exit and is then cleared with `release-locks` ([Liquibase docs](https://docs.liquibase.com/secure/user-guide-5-1/what-is-the-database-changelog-lock-table)) | per changeset |
| **Rails / ActiveRecord** | `pg_try_advisory_lock` on a key derived from the database name. It raises `ConcurrentMigrationError` if the lock is taken, then reloads `schema_migrations` "to be sure it wasn't changed by another process before we got the lock" ([`migration.rb`](https://github.com/rails/rails/blob/main/activerecord/lib/active_record/migration.rb), [`postgresql_adapter.rb`](https://github.com/rails/rails/blob/main/activerecord/lib/active_record/connection_adapters/postgresql_adapter.rb)). It can be turned off with `advisory_locks: false` ([Rails guides](https://guides.rubyonrails.org/configuring.html#configuring-a-postgresql-database)) | per migration, unless `disable_ddl_transaction!` |
| **Django** | no lock found in the migration executor ([`executor.py`](https://github.com/django/django/blob/main/django/db/migrations/executor.py)), and none is described in the migrations docs ([Django docs, Migrations](https://docs.djangoproject.com/en/stable/topics/migrations/)). That Django has none anywhere is *unverified* | on PostgreSQL "all migration operations will run inside a single transaction by default"; `atomic = False` opts out (same docs) |
| **Prisma Migrate** | `SELECT pg_advisory_lock(72707369)` with a fixed 10 s timeout ([prisma-engines `flavour/postgres.rs`](https://github.com/prisma/prisma-engines/blob/main/schema-engine/connectors/sql-schema-connector/src/flavour/postgres.rs)). The docs call it "purely to avoid catastrophic errors"; it can be disabled with `PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK` ([Prisma docs, Advisory locking](https://www.prisma.io/docs/orm/prisma-migrate/workflows/development-and-production#advisory-locking)) | *unverified* |
| **golang-migrate** | `pg_advisory_lock` on a CRC32 of database, schema and table names ([`database/postgres/postgres.go`](https://github.com/golang-migrate/migrate/blob/master/database/postgres/postgres.go), [`database/util.go`](https://github.com/golang-migrate/migrate/blob/master/database/util.go), [FAQ](https://github.com/golang-migrate/migrate/blob/master/FAQ.md)) | the file runs as written; the README says to wrap multi-statement migrations in `BEGIN`/`COMMIT` yourself ([postgres README](https://github.com/golang-migrate/migrate/blob/master/database/postgres/README.md)) |
| **Sqitch** | `pg_advisory_lock(75474063)` (or `pg_try_`), plus `LOCK TABLE changes IN EXCLUSIVE MODE` per change "to allow only one change at a time" ([`Engine/pg.pm`](https://github.com/sqitchers/sqitch/blob/main/lib/App/Sqitch/Engine/pg.pm)) | per change |

Every lock here guards the **migration bookkeeping against a second migrator**. None keeps application traffic out.

### 5. Old and new versions side by side: expand/contract

- **Expand/contract** ("parallel change") splits a backward-incompatible change into three phases: expand, migrate, contract ([Danilo Sato on martinfowler.com, Parallel Change](https://martinfowler.com/bliki/ParallelChange.html)). For schemas, a release first adds things (new column, new table) that old code ignores. Code moves over in later releases, and the old column is dropped only once no running version uses it.
- **strong_migrations** applies this to dropping a column. Active Record "caches database columns at runtime, so if you drop a column, it can cause exceptions until your app reboots", so the column is first put in `ignored_columns`, that code is deployed, and only then is the column removed ([strong_migrations README, Removing a column](https://github.com/ankane/strong_migrations/blob/master/README.md#removing-a-column)). The README lists the operations that block reads or writes and gives a safe alternative for each.
- **pgroll** serves "multiple schema versions simultaneously" through views. `start` applies the additive changes, backfills new columns and installs triggers that copy writes between old and new columns. Each client picks its version through `search_path`, and `complete` removes the old version "once there are no more client applications using the old schema version" ([pgroll README](https://github.com/xataio/pgroll/blob/main/README.md)).
- **Reshape** works the same way, through views and triggers, in three phases: `migration start`, roll out the app, then `migration complete` or `abort` ([Reshape README](https://github.com/fabianlindfors/reshape/blob/main/README.md)).
- **Maintenance window / stop-the-world**: stop all old instances, migrate, start the new ones. It avoids the compatibility rules at the cost of downtime. Rolling deploys exist to avoid that, which is why the tools above move the compatibility work into the migrations instead.

### 6. How an old version notices a newer schema

- **Flyway tolerates it by default.** A migration applied in the database but missing locally, with a version above the highest local one, is in state `FUTURE_SUCCESS`, "most likely successfully installed by a future version of this deployable" ([Flyway `MigrationState.java`](https://github.com/flyway/flyway/blob/main/flyway-core/src/main/java/org/flywaydb/core/api/MigrationState.java)). `ignoreMigrationPatterns` defaults to `*:future`, so validation passes ([Flyway `FlywayModel.java`](https://github.com/flyway/flyway/blob/main/flyway-core/src/main/java/org/flywaydb/core/internal/configuration/models/FlywayModel.java)). That default only makes sense if migrations are backwards compatible.
- **pgroll** handles it structurally: an old client keeps its own versioned schema in `search_path` until `complete` ([pgroll README](https://github.com/xataio/pgroll/blob/main/README.md)).
- **Rails** does not check at runtime for this case. The guidance is to make old code stop depending on a column before the column is dropped ([strong_migrations README](https://github.com/ankane/strong_migrations/blob/master/README.md#removing-a-column)).
- A check made only at startup or connect time, which is what this repo has (section 7), says nothing about a migration that runs later while the process keeps its connections. Catching that needs either a repeated check or migrations that never break the running version.

## What this means for Family Agenda

**How it works today** ([`database.ts`](../../packages/adapters/src/postgres/database.ts), [`supplied-families.ts`](../../apps/api/src/context/supplied-families.ts), ADR-0003 amendment "Preparing on opening"):

- `migrate()` checks out one pool client and takes `pg_advisory_lock(7342001)` on it, which waits with no timeout. Under the lock it refuses an old or newer history, then runs `migrateFamily`. That calls drizzle's `dialect.migrate`, which runs all pending migrations in one transaction on *another* pool connection. The lock is released in `finally`.
- Because advisory locks are per database, key 7342001 serialises the migrators of one Family database across all cores without making different Families wait on each other.
- Transactional DDL makes each prepare all-or-nothing, and the second migrator, once it gets the lock, re-reads the history and finds nothing to do. So "nothing is prepared twice" holds.
- Within one core, `#preparing` makes requests for that database wait. Across cores, other cores' requests are held back only by the table locks the DDL takes, which cover the touched tables until commit.
- The gap is **afterwards**. A core checks the schema only when it *opens* a Family (`openPreparedFamily`: `refuseNewerMigrationHistory`, `isSchemaCurrent`). An older core that already has the Family open keeps serving it on the new schema until it has been idle for 5 minutes. A newer core keeps the Family busy if it receives regular requests, which is the case during a rolling update. The 409 path does not cover this case. The repo's migrations include breaking ones: `0004` drops a table and `0009` renames `public_id` to `family_id`. Either would break an older core that is still serving.

**Options:**

| Option | What it buys | Costs and limits |
|---|---|---|
| **A. Exclusive database lock** (`ALLOW_CONNECTIONS false` / `REVOKE CONNECT` + `pg_terminate_backend`) | true stop-the-world | needs owner rights or `pg_signal_backend` on every Family database, kills in-flight requests, also shuts out *newer* cores and the migrator's own new connections; not what any reviewed tool does. Also not needed: the DDL's own locks already exclude the touched tables during the migration |
| **B. Shared advisory lock per request** (`pg_advisory_xact_lock_shared(7342001)` in a transaction around each request, against the migrator's exclusive one) | old cores' requests wait for an in-flight migration instead of failing against it | one extra round trip and a pinned connection per request. A request holding the shared lock blocks the migration, and because of arrival order a *waiting* migration then blocks every new request: the lock-queue problem, moved to the advisory lock. Long requests (Source runs) would hold migrations back. **It protects nothing after the commit**, which is where the real risk is |
| **C. Schema check on a reused Family** (re-read `drizzle.__drizzle_migrations` count/last hash when a request reuses an opened Family, at most every few seconds) | an older core notices a newer migration while running, drops the opened Family and answers `409 migrated-by-newer-release`, so the caller tries another core, as on first opening | one small indexed query per request, or less with a short cache. There is a window of up to the cache interval, and a request already in flight may still hit the new schema |
| **D. Expand/contract rules for migrations** | old and new cores can serve one Family side by side, so the window in C stops mattering | discipline: a release only adds things (nullable or defaulted columns, new tables, new indexes); drops and renames come at least one release after the code stopped using them (`0009` would have been add + copy + later drop); no data rewrite the old code cannot read. Could be checked in CI against the migration SQL |
| **E. `lock_timeout` on the migration** (`SET LOCAL lock_timeout = '5s'` inside drizzle's transaction, e.g. as the first statement of the first pending migration, with a retry of the whole prepare) | a migration stuck behind a long transaction of another core fails fast instead of stalling every request on that table | an occasional retry. drizzle offers no hook for it, so it has to be injected the way `migrateFamily` already injects the Family id |
| **F. Nothing beyond the current lock** | simplest | correct for serialising migrators, but an older core that keeps a Family open can run against a schema it does not know, for up to 5 minutes after its last request |

**Recommendation: do not lock the Family database against other cores.** Keep the exclusive session advisory lock for the migrator only, which is the same model as Rails, Prisma, golang-migrate, Sqitch and Flyway, and add three things:

1. **E:** a `lock_timeout` on the migration transaction, with a retry.
2. **C:** a cheap schema-version check when a cached Family is reused (throttled), so an older core drops a Family that a newer release migrated and answers the existing 409.
3. **D:** a written expand/contract rule for migrations. It turns the 409 from a correctness guarantee into a fallback and lets rolling updates run without failed requests.

Option B (shared advisory lock per request) is not worth it: it costs every request, recreates the lock-queue problem, and does not cover the time after the migration commits. Option A is the stop-the-world approach and fits neither rolling updates nor a core's privileges.

**Does Postgres have built-in means?** It has the pieces, not a feature. Advisory locks are only as strong as every client's cooperation. DDL locks and transactional DDL give atomic migrations and exclude the touched tables while the migration runs. `lock_timeout` bounds the waiting. Connection controls plus `pg_terminate_backend` can shut a database, but only with owner or signal privileges, and in-flight work is killed.
