# Portainer: deploying and updating the stack from a registry image

Question (issue #194, part of map #192): how does Portainer deploy and update `compose.yaml` when its services use `image: ghcr.io/artkoenig/family-agenda:<tag>`, for a public and for a private GHCR package?

Research date: 2026-11-06 (revised after `docs.portainer.io`, `docs.github.com` and `docs.docker.com` became reachable; every claim below was read on the cited page, Portainer docs version 2.45 LTS, unless noted). Open items from the first draft are resolved in place.

## What `compose.yaml` needs for this to work (from the repo, verified)

- Today `x-app` has `build: .` and `image: family-agenda:local`, and `mdns` uses `image: family-agenda:local`. A stack pasted into Portainer's web editor has no build context, so a registry deployment needs a separate compose file (or an override) whose `api`, `worker` and `mdns` all say `image: ghcr.io/artkoenig/family-agenda:<tag>` and no `build:`.
- `api`, `worker` and `mdns` share one image. They must be moved to the same tag together; with a single YAML anchor or a `${FAMILY_AGENDA_IMAGE}`-style variable that is one edit.
- `mdns` uses `network_mode: host`, `worker` uses `init: true`, and seven named volumes are declared (`postgres-data`, `master-key`, `blobs`, `plugins`, `tessdata`, `matrix-instance`, `matrix-data`).

## Findings

### 1. Web editor stack versus Git repository stack

- Four ways to create a stack: web editor, upload, Git repository, custom template ([Add a new stack](https://docs.portainer.io/user/docker/stacks/add)).
- A web-editor or uploaded stack stores its compose file in Portainer and is edited in the stack's Editor tab, which also has a version dropdown, an environment-variables section and a webhook toggle ([Inspect or edit a stack](https://docs.portainer.io/user/docker/stacks/edit)). The Family copies the file once and owns it. Compose changes in a later release are not picked up unless the Family pastes them in.
- A Git stack uses a **Source** (a preconfigured Git repository entry), a reference (for example a branch) and a Compose path; extra YAML files can be merged like repeated `-f` options ([Add a new stack, option 3](https://docs.portainer.io/user/docker/stacks/add)). The compose file edits live in the repository. A stack can later be detached from Git, which copies only the main compose file into Portainer ([Inspect or edit a stack](https://docs.portainer.io/user/docker/stacks/edit)).
- **Git authentication (private repository).** A Git Source has an Authentication toggle with a username and a personal access token or password; the token needs repository read permission. Shared credentials can be reused. Without the toggle (a public repository) no credentials are needed ([Add a new Git Repository source](https://docs.portainer.io/user/app-delivery/sources/git), [token scopes FAQ](https://docs.portainer.io/faqs/getting-started/what-scopes-are-required-for-github-gitlab-and-bitbucket-tokens), linked from that page, not read). While the repository is private, a Git stack therefore needs the Family to hold a token for it. Whether Families should follow the Git repository at all is a decision for #192.
- **Environment variables.** The stack form has an environment-variables section where variables are set one by one or loaded with **Load variables from .env file**. They are available to `${VAR}` substitutions in the compose file, which itself is not modified. On Docker Standalone and Podman, `stack.env` can also be named as an `env_file` to pass all of them into containers ([Add a new stack](https://docs.portainer.io/user/docker/stacks/add)). For a Git stack, Portainer ignores other repository files except the `.env` file, which is processed if it exists and no variables were defined before ([How do automatic updates work?](https://docs.portainer.io/faqs/troubleshooting/stacks-deployments-and-updates/how-do-automatic-updates-for-stacks-applications-work)). This covers the `${PORT:-8080}`-style variables in `compose.yaml` (`PORT`, `PUBLIC_URL`, `POSTGRES_PASSWORD`, `TZ`, `MDNS_NAME`, `TRUST_PROXY`).

### 2. Updates: moving tag versus exact version

- **Git stack, GitOps updates.** Mechanism is *polling* (fetch interval) or *webhook* (a URL, for example called from GitHub Actions). Portainer compares the latest commit hash with the one stored at the last deploy and, if equal, does nothing. If different, it re-runs Compose; for all platforms it does not force a redeployment if the image did not change ([How do automatic updates work?](https://docs.portainer.io/faqs/troubleshooting/stacks-deployments-and-updates/how-do-automatic-updates-for-stacks-applications-work)).
- GitOps settings **Re-pull image** ("always pull the most recent version of container images when updating the stack, equivalent to `--pull=always`") and **Force redeployment** (redeploy at every interval or webhook call even with no change in Git; without it, updates trigger only when the remote repository changed) ([Add a new stack](https://docs.portainer.io/user/docker/stacks/add)). For a moving tag, polling a Git ref never notices a registry change, so a moving-tag Git stack needs **Force redeployment together with Re-pull image**.
- Manual **Pull and redeploy** is always a forced redeploy, with an optional **Re-pull image and redeploy** toggle that makes Docker fetch the latest images even if a copy exists locally; it may interrupt service ([Inspect or edit a stack](https://docs.portainer.io/user/docker/stacks/edit), automatic-updates FAQ above).
- **Web-editor stack, Update dialog.** The 2.45 page for editing a web-editor stack lists the Editor tab, the Environment variables section, the webhook toggle, **Prune services** and **Update the stack**. It documents **no re-pull toggle** for web-editor stacks; the re-pull toggle is documented only for Git stacks ([Inspect or edit a stack](https://docs.portainer.io/user/docker/stacks/edit)). Whether the UI nevertheless shows one was not verifiable from docs. So for a web-editor stack, updating a moving tag in Community Edition is not documented to re-pull.
- **Stack webhooks** ([Webhooks](https://docs.portainer.io/user/docker/stacks/webhooks)): the page states "This functionality is only available in Portainer Business Edition." A webhook is a POST to `/api/stacks/webhooks/<id>`; a call "redeploy[s] stack containers with latest image of same tag", `?tag=<tag>` switches the image tag, and `?pullimage=false` (itself Business Edition only) suppresses the pull, so **by default a webhook call pulls images**. Extra query parameters become compose variables (the page's example is `image: repository/image:${SERVICE_TAG:-stable}` with `?SERVICE_TAG=development`), which suits a channel switch. **Not available in Community Edition**, so a Community Edition Family cannot get registry-push-triggered redeploys from this.
- **Exact version.** Edit the tag (or Git ref) and redeploy; all three services move together if they share one variable. Nothing is pulled silently.
- **Image update indicators.** The stack page shows an indicator per container; reload rechecks all or one ([Inspect or edit a stack](https://docs.portainer.io/user/docker/stacks/edit)). It compares the local and remote image digest on page refresh, with caching, with green tick, orange cross and grey hyphen states, and is documented as Business Edition only ([How does the image update notification icon work?](https://docs.portainer.io/faqs/troubleshooting/stacks-deployments-and-updates/how-does-the-image-update-notification-icon-work), first-draft extract; not re-read).
- Net for Community Edition: a Family on the moving channel reliably updates via Git stack with Force redeployment + Re-pull image, or by hand through Pull and redeploy with re-pull. Exact-version Families edit the tag.

### 3. Constraints of this stack under Portainer

- On Docker Standalone, Portainer runs `docker compose up` on the file ([How do automatic updates work?](https://docs.portainer.io/faqs/troubleshooting/stacks-deployments-and-updates/how-do-automatic-updates-for-stacks-applications-work)), so `network_mode: host`, `init: true`, YAML anchors and `depends_on` conditions are handled by Compose as on the CLI. No Portainer page restricts them (none mentions them). The `mdns` Linux-host caveat in `compose.yaml` still applies. A shared image across services is just several services with the same image reference.
- **Volume names.** Compose prefixes named volumes with the project name. Compose's precedence for the project name, highest first: `-p` flag, `COMPOSE_PROJECT_NAME`, top-level `name:`, then the directory name ([Specify a project name](https://docs.docker.com/compose/how-tos/project-name/)). Portainer's Compose deployer builds the project with `cli.WithName(options.ProjectName)` ([portainer `pkg/libstack/compose/composeplugin.go`](https://github.com/portainer/portainer/blob/develop/pkg/libstack/compose/composeplugin.go), source read on the `develop` branch), which is an explicit name option that takes the place of the file's `name:`. Hence the Portainer **stack name** decides the prefix and `name: family-agenda` in the file does not. That `ProjectName` is the stack name, and whether Portainer alters its characters, was not checked in the source. Practical rule: name the stack `family-agenda` for the `family-agenda_*` volumes of the release notes to match; a differently named stack starts with empty volumes.
- Relative bind mounts break on Git stack redeploys, and the relative-path-volumes feature is Business Edition ([Add a new stack](https://docs.portainer.io/user/docker/stacks/add)); this stack uses only named volumes, so it is unaffected.
- A forced re-pull redeploys the stack, which recreates changed containers (the first draft's claim that `postgres` is always recreated is dropped: Compose recreates only services whose configuration or image changed). Data is on named volumes.

### 4. Pulling from GHCR

- **Public package:** "public packages allow anonymous access and can be pulled without authentication or signing in via the CLI" ([Working with the Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry), [About inheritance of access permissions](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility)). No registry needs to be configured in Portainer.
- **Private package:** the registry needs authentication with a personal access token (classic) with at least `read:packages`; fine-grained tokens are not supported by GitHub Packages ([Working with the Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)). In Portainer:
  - Registries, **Add a custom registry** with URL `ghcr.io`, Authentication on, GitHub username and the token as password ([Add a custom registry](https://docs.portainer.io/admin/registries/add/custom)). This works in Community Edition.
  - The dedicated **GitHub** registry type is **Business Edition only** and asks for a token with `delete:packages`, `repo` and `write:packages` scopes ([Add a GitHub registry](https://docs.portainer.io/admin/registries/add/ghcr)), far wider than a pull needs. For a Family, prefer the custom registry with a `read:packages` token.
  - On the stack form, registries can be selected explicitly; by default all configured registries are used ([Add a new stack](https://docs.portainer.io/user/docker/stacks/add)).
- **Package visibility when the repository becomes public:** a package linked to a repository inherits the repository's access permissions "(but not the visibility)". A newly published package under a personal account defaults to private. Visibility is changed in the package's settings (Danger Zone, Change visibility) ([Configuring a package's access control and visibility](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility)). So making the repository public does **not** make the image public; the maintainer must set the package to public once, after the first publish. The install docs may promise "no credentials" only after that.
